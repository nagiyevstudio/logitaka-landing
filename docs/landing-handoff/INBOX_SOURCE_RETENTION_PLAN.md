# План исправления хранения исходников Inbox

## Целевое поведение

| Сценарий | Результат в проекте | Исходник |
|---|---|---|
| Аудиофайл загружен в Inbox | Расшифровка в Markdown | Временный файл удаляется после успешного сохранения результата. |
| Изображение загружено в Inbox для извлечения данных | Извлечённые данные в Markdown | Временный файл удаляется после успешного сохранения результата. |
| Изображение добавлено напрямую в проект, в том числе из обсуждения | Проектный материал с изображением | Изображение остаётся доступным в проекте. |

До успешной записи, включая выбор проекта и повтор после сбоя, Inbox хранит временный исходник для продолжения обработки.

## Текущее поведение в приложении

Проверенный маршрут проходит через `OS/apps/frontend/src/app/api/workflows/inbox/intake/route.ts` и диспетчер `server/inbox/intake-runtime.ts`. Обработчики `server/inbox/audio-runtime.ts` и `server/inbox/image-runtime.ts` при записи передают `preserveSourceBinary: true`. Поэтому общий `server/projects/document-ingest.ts` сохраняет в проекте Markdown и бинарный оригинал. Затем обработчик вызывает `deleteItemAsset` для временного файла Inbox. Ошибка этой очистки сейчас поглощается. Прямое добавление изображения из обсуждения явно запрашивает сохранение исходника в `server/chat-attachments/save-to-project.ts`.

Пути `server/…` здесь относительны к `OS/apps/frontend/src/` репозитория приложения.

## Изменение

1. В обработчиках аудио и изображений Inbox явно отключить сохранение бинарного оригинала при записи в проект. Сохранить извлечение, Markdown и индекс, ссылку из Inbox, выбор проекта и существующий идентификатор операции. Сохранение изображения при прямом добавлении оставить на действующем проектном маршруте.
2. После подтверждённой записи Markdown удалить временный файл Inbox. Использовать текущие границы записи и очистки. Сбой удаления должен оставлять результат доступным и давать способ повторить только очистку. Учесть прерывание между записью результата, удалением файла и обновлением метаданных. Уже удалённый файл считать успешно очищенным. Возобновление должно использовать существующую запись, чтобы избежать второго документа и повторной обработки.
3. Проверить маршруты ручного выбора проекта, повтора и отмены пакета. До успешной записи сохранить исходник для повтора. При отмене использовать действующий сброс временных файлов пакета. Если в развёрнутой среде есть отдельный обработчик этих загрузок, проверить там те же условия.
4. Обновить §12.7 `OS/Core/.agent/capabilities/logitaka.md` вместе с реализацией. Описать удаление временного исходника двух сценариев Inbox после успеха и доступность изображения, добавленного напрямую в проект. Статус уже сохранённых проектных оригиналов вынести в отдельное решение перед любой исторической очисткой.

## Приёмка

- Аудиофайл и изображение в Inbox дают по одному доступному для поиска Markdown-документу. После успешной обработки нет бинарной копии в проекте и временного файла в Inbox. Для документа не создаётся ссылка на исходный бинарный файл.
- Файл, для которого сначала нужно выбрать проект, и файл после ошибки до записи можно обработать повторно с тем же исходником. Успешный повтор создаёт один документ и очищает временный файл.
- Имитированный сбой удаления или остановка в момент очистки оставляет Markdown доступным. Повтор очистки удаляет остаток и приводит метаданные в согласованное состояние без повторной обработки.
- Изображение, добавленное прямо в проект, по-прежнему открывается как изображение. Для проверки использовать существующие тесты `server/inbox/__tests__/audio-runtime.test.ts`, тесты пакетной обработки Inbox, `server/projects/__tests__/document-engine.test.ts` и `server/chat-attachments/__tests__/save-to-project.test.ts`. Проверки Inbox, ожидающие сохранения исходника, привести к новому поведению.
